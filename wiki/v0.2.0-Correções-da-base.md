# v0.2.0 — Correções da base

> Status: **a publicar** · Versão anterior: [[v0.1.0|v0.1.0-Versão-original]]

Revisão do `docker-compose.yml` da v0.1.0 antes de começar o caso Pauta Digital. O objetivo foi deixar a base **portável** (roda igual em qualquer máquina), **previsível** (não muda sozinha com o tempo) e **segura o bastante** para um repositório público.

## Resumo

### Adicionando
* `.env.example` com todas as variáveis (usuário, senhas, banco e portas) e `.gitignore` ignorando o `.env`
* Healthcheck no PostgreSQL com `pg_isready`
* `pgadmin/servers.json`: o pgAdmin já abre com o servidor cadastrado
* Volume próprio para o pgAdmin (`pgadmin-data`)
* `initdb/01_extensoes.sql`, que ativa a extensão `pg_stat_statements`
* Nome de projeto fixo no compose (`name: pauta-digital`) e nomes de container (`pauta-postgres`, `pauta-pgadmin`)
* Documentação do caso: `docs/caso-de-negocio.md`, `docs/modelo-de-dados.md` e `docs/decisoes.md`

### Modificando
* Serviços renomeados: `teste-postgres-compose` → `postgres` e `teste-pgadmin-compose` → `pgadmin`
* Imagens com versão fixa: `postgres` → `postgres:18` e `dpage/pgadmin4:latest` → `dpage/pgadmin4:9`
* Volume do banco: pasta da máquina local → volume nomeado `pgdata`
* Senhas, usuário e portas: valores fixos no compose → variáveis do `.env`
* `depends_on` do pgAdmin: espera o banco ficar saudável, não só o container iniciar
* README reescrito para o caso Pauta Digital, com comandos `docker compose` (v2) e URL de clone correta

### Removendo
* `version: '3'` (obsoleto no Compose v2)
* Senhas escritas diretamente no `docker-compose.yml`
* Caminho absoluto `/home/rneto/Desenvolvimento/...` no volume

## Detalhes de cada correção

### 1. Host do banco não batia com o README

**Problema:** o README mandava conectar no host `postgres`, mas o serviço se chamava `teste-postgres-compose`. Quem seguisse o passo a passo não conseguia conectar pelo pgAdmin.

**Solução:** o serviço foi renomeado para `postgres`. Dentro da rede do compose, o nome do serviço é o hostname, então README e compose passam a concordar.

---

### 2. Volume preso à máquina do autor

**Problema:** o volume era um bind mount para `/home/rneto/Desenvolvimento/Docker-Compose/PostgreSQL`. Em outra máquina, o Docker cria uma pasta nesse caminho (no Linux) ou falha (no Windows ou macOS).

**Solução:** volume nomeado, gerenciado pelo Docker.

```yaml
# antes
volumes:
  - /home/rneto/Desenvolvimento/Docker-Compose/PostgreSQL:/var/lib/postgresql/data

# depois
volumes:
  - pgdata:/var/lib/postgresql
```

**Por que `/var/lib/postgresql` e não `/data`:** a partir do Postgres 18, a imagem oficial guarda os dados em `/var/lib/postgresql/18/docker`, um subdiretório por versão maior. Montando o diretório pai, o volume funciona com o layout novo e facilita futuras atualizações com `pg_upgrade`.

---

### 3. Imagens sem versão fixa

**Problema:** `postgres` sem tag e `pgadmin4:latest` apontam para a versão mais recente do momento. Uma versão maior nova pode chegar sem aviso. Foi o caso do Postgres 18, que mudou o diretório de dados e quebrou o volume antigo.

**Solução:** `postgres:18` e `dpage/pgadmin4:9`. A tag de versão maior recebe correções de segurança, mas não muda de versão maior sozinha. Atualizar passa a ser uma decisão explícita.

---

### 4. Senhas no código

**Problema:** `testando123` estava versionada no repositório público.

**Solução:** as variáveis ficam em `.env`, que não é versionado. O repositório traz apenas o `.env.example`. O compose usa a sintaxe `${VAR:?mensagem}`: se a senha não estiver definida, ele **recusa subir** e diz o que falta, em vez de usar um valor padrão inseguro.

```yaml
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?defina POSTGRES_PASSWORD no arquivo .env}
```

---

### 5. pgAdmin subia antes do banco estar pronto

**Problema:** `depends_on` simples só espera o *container* do banco iniciar, não o *Postgres* aceitar conexões.

**Solução:** healthcheck no banco e `condition: service_healthy` no pgAdmin.

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
```

**Detalhe do `-h 127.0.0.1`:** na primeira subida, a imagem roda um servidor temporário, só por socket local, enquanto executa os scripts de `initdb/`. Sem o `-h`, o `pg_isready` responderia "pronto" durante essa fase. Forçando TCP, o banco só é marcado como saudável quando o servidor definitivo está no ar.

---

### 6. Servidor do pgAdmin precisava ser cadastrado na mão

**Problema:** a cada recriação do container, era preciso cadastrar o servidor de novo, porque o pgAdmin não tinha volume.

**Solução:**
- Volume `pgadmin-data` para persistir configurações e sessões
- `pgadmin/servers.json`, importado na primeira subida: o servidor **Pauta Digital (local)** já aparece no grupo *Laboratório*

A senha do banco não fica no `servers.json`. O pgAdmin pede no primeiro acesso, e você pode salvá-la.

---

### 7. Monitoramento de consultas

**Adição:** a extensão `pg_stat_statements` é carregada na inicialização (`shared_preload_libraries`) e criada por `initdb/01_extensoes.sql`. Ela será usada nas análises de performance das próximas versões.

```sql
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;
```

## Migrando da v0.1.0

Algumas mudanças quebram a compatibilidade com a versão anterior.

1. **Crie o `.env`:** `cp .env.example .env` e defina as senhas. Sem isso, o compose não sobe.
2. **Remova os containers antigos:** eles têm outros nomes e ocupam as mesmas portas.
   ```bash
   docker ps -a                      # localize os containers teste-*
   docker rm -f <nome-do-container>
   ```
3. **Dados antigos não são migrados automaticamente.** Eles continuam na pasta do bind mount antigo e eram de outra versão do Postgres. Se precisar deles, faça um `pg_dump` no ambiente antigo e restaure no novo.
4. **Novo host no pgAdmin:** `postgres` (já vem configurado).
